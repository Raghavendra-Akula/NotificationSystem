# Distributed Notification Lab — API Contract v0.1

This contract defines the first REST/JSON API for the local learning system. It uses the services and event flow described in the existing requirements, event contracts, data model, architecture, and deployment documents. It does not add trading, broker, real push, or email integrations.

## 1. Conventions

- Base path: `/api/v1`
- Content type: `application/json`
- Timestamps: RFC 3339 UTC strings, for example `2026-11-11T10:15:30Z`.
- IDs: opaque strings generated by the caller for source `eventId`s, or by the service for resource IDs.
- Symbols are trimmed and normalized to uppercase.
- A `userId` identifies a simulated dashboard user only. It is not a broker account or an authenticated identity.
- `traceId` is optional on event submissions. The API creates one when omitted and carries it with the event and subsequent notification work.
- Event submission returns `202 Accepted` once the source event has been accepted by the configured event transport. Evaluation and notification delivery continue asynchronously.
- Duplicate source events are idempotent by `(source, eventId)`. A replay can still receive `202`; it does not create a second logical notification.
- Notification status values are `ACCEPTED`, `QUEUED`, `SENT_TO_PROVIDER`, and `FAILED`. `SENT_TO_PROVIDER` means the mock provider accepted the request; it does not confirm display on a device.

## 2. Price alerts

### Create an alert

`POST /api/v1/price-alerts`

**Handler:** Notification API. **Work:** synchronous PostgreSQL insert; no event is queued.

Request:

```json
{
  "userId": "demo-user-1",
  "symbol": "AAPL",
  "direction": "ABOVE",
  "threshold": 205.5
}
```

`direction` is `ABOVE` or `BELOW`. The new alert is one-shot and starts `ACTIVE`.

Success: `201 Created`

```json
{
  "alertId": "alrt_01J...",
  "userId": "demo-user-1",
  "symbol": "AAPL",
  "direction": "ABOVE",
  "threshold": 205.5,
  "status": "ACTIVE",
  "createdAt": "2026-11-11T10:15:30Z"
}
```

Errors: `400` malformed JSON; `422` invalid or missing fields; `500` unexpected persistence error.

### List alerts

`GET /api/v1/price-alerts?userId=demo-user-1&status=ACTIVE&limit=50&cursor=...`

**Handler:** Notification API. **Work:** synchronous PostgreSQL read.

All query parameters are optional. `status` is `ACTIVE`, `FIRED`, or `CANCELLED`. `limit` defaults to 50 and must be 1–100. `cursor` is an opaque continuation token.

Success: `200 OK`

```json
{
  "items": [
    {
      "alertId": "alrt_01J...",
      "userId": "demo-user-1",
      "symbol": "AAPL",
      "direction": "ABOVE",
      "threshold": 205.5,
      "status": "ACTIVE",
      "createdAt": "2026-11-11T10:15:30Z"
    }
  ],
  "nextCursor": null
}
```

Errors: `400` invalid query parameter; `500` unexpected read error.

### Cancel an alert

`POST /api/v1/price-alerts/{alertId}/cancel`

**Handler:** Notification API. **Work:** synchronous conditional PostgreSQL update.

No request body is required. Only an `ACTIVE` alert can transition to `CANCELLED`; the update is conditional so it cannot overwrite a concurrent firing.

Success: `200 OK`

```json
{
  "alertId": "alrt_01J...",
  "status": "CANCELLED",
  "cancelledAt": "2026-11-11T10:16:00Z"
}
```

Errors: `404` alert not found; `409` alert is already `FIRED` or `CANCELLED`; `500` unexpected persistence error.

## 3. Simulated events

Event submission acknowledges transport acceptance, not evaluation or notification delivery. The event evaluator records `(source, eventId)` under a database uniqueness constraint. It acknowledges broker work only after its database transaction commits. A repeated event ID for the same source is ignored by evaluation.

### Submit a simulated price event

`POST /api/v1/simulated/price-events`

**Handler:** Notification API / market-event ingress. **Work:** synchronous validation and publish; queued evaluation.

Request:

```json
{
  "eventId": "price-demo-00042",
  "symbol": "AAPL",
  "price": 206.1,
  "sourceSequence": 42,
  "occurredAt": "2026-11-11T10:15:30Z",
  "traceId": "trace-demo-01"
}
```

`eventId` is stable across retries. `sourceSequence` is a positive, per-symbol sequence number. `occurredAt` is the simulator's event time. `traceId` may be omitted.

Success: `202 Accepted`

```json
{
  "eventId": "price-demo-00042",
  "traceId": "trace-demo-01",
  "status": "ACCEPTED",
  "acceptedAt": "2026-11-11T10:15:31Z"
}
```

The first accepted quote for a symbol establishes its baseline and does not count as a threshold crossing. Stale or out-of-order sequence handling is performed by the evaluator and recorded for observation; this response does not promise that the event will fire an alert.

Errors: `400` malformed JSON; `422` invalid event fields; `503` event transport unavailable (the event was not accepted).

### Submit a simulated order execution event

`POST /api/v1/simulated/order-events`

**Handler:** Notification API / order-event ingress. **Work:** synchronous validation and publish; queued evaluation.

Request:

```json
{
  "eventId": "exec-demo-00017",
  "userId": "demo-user-1",
  "orderId": "order-demo-7",
  "symbol": "AAPL",
  "executionStatus": "PARTIALLY_FILLED",
  "quantity": 3,
  "price": 205.9,
  "occurredAt": "2026-11-11T10:15:30Z",
  "traceId": "trace-demo-02"
}
```

`executionStatus` is `PARTIALLY_FILLED` or `FILLED`; `quantity` and `price` must be positive. `eventId` is stable across retries. `traceId` may be omitted.

Success: `202 Accepted`

```json
{
  "eventId": "exec-demo-00017",
  "traceId": "trace-demo-02",
  "status": "ACCEPTED",
  "acceptedAt": "2026-11-11T10:15:31Z"
}
```

A new execution event is evaluated asynchronously and creates one logical notification keyed to its source event. A replay of that source event does not create another.

Errors: `400` malformed JSON; `422` invalid event fields; `503` event transport unavailable (the event was not accepted).

## 4. Notification history and status

### List notification history

`GET /api/v1/notifications?userId=demo-user-1&status=QUEUED&limit=50&cursor=...`

**Handler:** Notification API. **Work:** synchronous PostgreSQL read; delivery proceeds independently.

All query parameters are optional. `status` is one of `ACCEPTED`, `QUEUED`, `SENT_TO_PROVIDER`, or `FAILED`. `limit` defaults to 50 and must be 1–100. Results are newest first; `cursor` is opaque.

Success: `200 OK`

```json
{
  "items": [
    {
      "notificationId": "ntfn_01J...",
      "dedupeKey": "alert:alrt_01J...",
      "userId": "demo-user-1",
      "source": "PRICE_ALERT",
      "sourceEventId": "price-demo-00042",
      "traceId": "trace-demo-01",
      "status": "QUEUED",
      "createdAt": "2026-11-11T10:15:32Z",
      "updatedAt": "2026-11-11T10:15:32Z"
    }
  ],
  "nextCursor": null
}
```

Errors: `400` invalid query parameter; `500` unexpected read error.

### Get notification status and timeline

`GET /api/v1/notifications/{notificationId}`

**Handler:** Notification API. **Work:** synchronous PostgreSQL read.

Success: `200 OK`

```json
{
  "notificationId": "ntfn_01J...",
  "dedupeKey": "alert:alrt_01J...",
  "userId": "demo-user-1",
  "source": "PRICE_ALERT",
  "sourceEventId": "price-demo-00042",
  "traceId": "trace-demo-01",
  "status": "SENT_TO_PROVIDER",
  "createdAt": "2026-11-11T10:15:32Z",
  "updatedAt": "2026-11-11T10:15:34Z",
  "attempts": [
    {
      "attemptNumber": 1,
      "startedAt": "2026-11-11T10:15:33Z",
      "completedAt": "2026-11-11T10:15:34Z",
      "result": "ACCEPTED",
      "providerRequestId": "mock_01J..."
    }
  ]
}
```

Attempt results may include `ACCEPTED`, `TEMPORARY_FAILURE`, or `PERMANENT_FAILURE`; provider error details should be safe for display and must not contain secrets. A provider acceptance does not prove device display.

Errors: `404` notification not found; `500` unexpected read error.

## 5. Health checks

### Liveness

`GET /health/live`

**Handler:** API process. **Work:** synchronous in-process check; no database or queue call.

Healthy: `200 OK`

```json
{"status":"ok"}
```

### Readiness

`GET /health/ready`

**Handler:** API process. **Work:** synchronous dependency check of PostgreSQL and the configured event transport.

Ready: `200 OK`

```json
{"status":"ready","checks":{"postgres":"ok","eventTransport":"ok"}}
```

Not ready: `503 Service Unavailable`

```json
{"status":"not_ready","checks":{"postgres":"ok","eventTransport":"unavailable"}}
```

## 6. Error response shape

Errors use a consistent JSON body. `code` is stable for clients; `message` is safe to display. Field validation errors include a JSON path and a short reason.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed.",
    "details": [
      {"field":"threshold","reason":"must be greater than zero"}
    ],
    "traceId": "trace-demo-01"
  }
}
```

Common codes include `INVALID_REQUEST`, `VALIDATION_ERROR`, `NOT_FOUND`, `STATE_CONFLICT`, `EVENT_TRANSPORT_UNAVAILABLE`, and `INTERNAL_ERROR`. The API must not return stack traces, credentials, or provider secrets.

## 7. Validation and behavior summary

- Required strings must be non-empty and within documented implementation limits; reject unknown enum values.
- `symbol` is normalized to uppercase. `threshold`, event `price`, and execution `quantity` must be positive finite numbers; reject NaN and infinity.
- Event timestamps must include a timezone. Sequence numbers and attempt numbers are positive integers.
- Event IDs are unique per source, not globally. The database uniqueness constraint is `(source, event_id)`; duplicate delivery is a successful no-op at evaluation.
- For a price event, the first quote per symbol is baseline only. Later stale or out-of-order sequences do not move the saved market state backward.
- The evaluator conditionally changes an alert from `ACTIVE` to `FIRED`. In one PostgreSQL transaction it records the event, alert transition, notification, and outbox row. A notification is created only if the conditional transition succeeds.
- Event/API acceptance, queueing, provider submission, and phone display are separate milestones. This API reports provider status only; it does not claim end-to-end exactly-once push delivery.

## 8. Scope notes and open policy

- The initial contract uses Pub/Sub in GCP and the Pub/Sub emulator locally behind the same event-ingress behavior.
- Retry count, retry schedule, and the final dead-letter handling policy are intentionally not part of this API contract. The existing requirements mention both a five-retry email outcome and an at-least-one-delivery expectation; the architecture and deployment docs specify bounded retries and a dead-letter path, while the required provider is mock push only. Resolve that policy before implementing delivery behavior.
- Authentication and authorization are not defined for this learning MVP. `userId` is a simulated identifier; do not use real account data.
